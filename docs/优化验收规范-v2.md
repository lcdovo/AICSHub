## 1. 验收目标与原则

验收回答四个问题：
1. 功能是否在真实业务状态上完成用户目标？
2. 不应发生的越权、未确认动作、重复副作用和信息泄漏是否被阻止？
3. 模型、检索、代码、数据和部署版本明确时，效果、速度与成本是否达到冻结指标？
4. 进程退出、连接断开、依赖故障和未知结果下，系统是否给出真实且可恢复的状态？

验收必须观察API/UI、工具出口、SQL事实、事件、模型账本和必要外部回执。只看最后一句回复、HTTP200、页面截图或测试数量均不足以证明任务成功。

本文阈值是候选目标，N0冻结版本后执行。若现实条件不满足，保持FAIL/BLOCKED并调整方案，不在看到结果后降低门槛或删去失败样本。

## 3. 验收状态与分级

### 3.1 状态

| 状态 | 定义 | 发布含义 |
| --- | --- | --- |
| NOT_RUN | 未按规定范围与层次执行 | 不通过 |
| PASS | 条件、环境、源码、数据和必要证据齐全且门槛满足 | 仅该项该范围通过 |
| FAIL | 实际执行但断言或质量/性能阈值未满足 | 阻止相关范围准入 |
| BLOCKED | 所需人工、额度、服务、数据或环境缺失，尚无法有效执行 | 不通过，不写成技术成功 |
| INVALID_EVIDENCE | 源码/数据漂移、证据缺失、分母不全或实验污染 | 保留诊断，不用于正式准入 |
| NOT_APPLICABLE | 明确排除范围，事前记录理由并由验收负责人确认 | 仅排除对应范围；不能事后规避失败 |

“PARTIAL”仅允许用于工作进度说明；正式矩阵须拆分为可判定条目。P0不能通过无依据N/A消失。

### 3.2 优先级

- P0：身份、权限、确认、幂等、证据版本、未知副作用、预算、隐私和可靠提交。固定场景必须全通过。
- P1：三条业务闭环、模型/检索/回答质量、必要前端、恢复/部署、声明容量。相关发布范围必须全部通过。
- P2：扩展交互、额外产品、视觉增强和辅助展示。允许明确延期，不影响其余已定义范围的判断。

| 层次 | 环境与手段 | 可以证明 | 不能证明 |

## 5. 执行环境与隔离

### 5.1 运行前清单

- 建立本次run_id、负责人、开始时间、目标DEV/AC2和数据版本。
- 使用冻结的隔离工作树或镜像；记录HEAD及未提交文件内容hash，不能只记录git commit。
- 核查源码、依赖、模型revision、量化、prompt/schema、策略、配置及数据hash。
- 当前数据库、Redis namespace、Milvus collection、对象存储桶和端口均有测试owner标记。
- 不连接业务库写测试，不运行导入清库、--clear、down -v或不明清理命令。
- 基线恢复、清理和备份路径与其他项目分开；不占用其他项目的8000/6379。
- 模型测试使用合成输入与允许外发的数据；无真实用户原文。
- 真实外部调用先校验本次固定授权与剩余额度；无授权时仅执行对应离线层。
- 记录数据库实际迁移头、客户端/服务端版本和Provider能力，不能只读取.env。
- 退出时核对活动槽、Job、未知业务、数据库/卷和原账本hash。

### 5.2 关键实验隔离

一次正式评测开始后，禁止其他开发任务修改其源码、数据、配置和标签。开发可在其他工作树继续，但不能挂载到同一评测容器。

源码开始/结束不一致时标INVALID_EVIDENCE；即使变化仅在Graph或分类器，Judge核心未变也不整体接受。可另开明确的组件诊断报告，但不能用局部结果抹除主报告失效。

### 6.2 标注与防泄漏

- 以语义家族、政策来源、产品情境和模板分组，禁止近重复或仅正反词交换跨开发/封存集。

- 正式集需真实人工逐例复核；G集需逐论断标注支持、矛盾、缺资料及必要遗漏。
- 至少一名人工复核者独立于标签自动生成；争议由第二人或领域负责人裁决，保留修改记录。

- 保存不可变数据、manifest、来源hash、reviewer、裁决时间、split_key和重复检查报告。
- 无独立人工资源时，模型质量正式项BLOCKED；仍可完成离线逻辑与诊断报告。

## 7. 指标定义与质量门槛

### 7.1 请求理解

| 指标 | 公式/分母 | 门槛 |
| --- | --- | --- |
| Macro-F1 | 预先冻结主题集合各类F1的算术平均；非法/超时计对应错误 | ≥0.90 |
| 请求类型准确率 | 完全正确请求类型数/全部300条 | ≥95% |
| 关键实体准确率 | 订单/产品/来源/明确空值组合完全正确数/全部300条 | ≥97% |
| 条件与多诉求 | 预先定义字段/顺序完全正确数/对应样本数；不只关键词命中 | 各≥95% |
| 有效结构率 | 至多一次修复后满足schema和绑定的结果/全部样本 | ≥99% |
| 歧义适当处理 | 真歧义场景的必要澄清/明确限制正确数/歧义集 | ≥95% |
| 固定动作保护 | S集相应未授权/未确认/重复动作次数 | 0 |

原始置信度不作为准入指标。不能将请求类型97.67%替代关键实体95.67%的失败。

### 7.2 检索

- Recall@20：对每个存在gold相关片段的问题，计算召回的相关片段数/gold片段数，再按问题平均；目标≥95%。
- nDCG@5：冻结相关度等级与理想排序；目标≥0.85。若只标二元相关度，报告明确使用0/1。
- 必要条件覆盖：最终送给生成和Judge的EvidenceBundle包含全部必要条件/例外的题数/具有这些条件的可回答题数；目标≥95%。
- 对无资料题不计算虚构Recall，单独统计错误匹配和可回答性判断；partial/unknown正确处理≥95%。
- 版本/权限错误片段返回数必须为0。
- dense/BM25/hybrid/rerank/rewrite消融采用同一封存范围；不能在每种模式选择不同最佳子集。
- 记录召回池、重排池、最终证据数量；top20命中不能替代top3最终证据完整性。

### 7.3 Judge与真实生成

| 指标 | 分母 | 门槛 |
| --- | --- | --- |
| 反例误放率 | 被错误允许发布的负候选/全部200负候选 | ≤2% |
| 正例误拒率 | 被拒绝或unknown的正确候选/全部200正候选 | ≤5% |
| 正确边界行为 | 正确允许的补问/有限回答/适当拒绝/全部100边界候选 | ≥95% |
| unknown率 | 结构/绑定/超时/依赖未知数/全部候选 | 总体及每个正式分层≤2% |
| 真实论断支持率 | 有充分当前证据支持的可核查论断/全部可核查论断 | ≥97% |
| 充分资料有效回答率 | 正确回答而非不必要拒答/120充分资料题 | ≥90% |
| 部分/无资料适当行为 | 正确有限回答、补问或拒答/各自40题 | 各≥95% |
| 必要条件保留率 | 回答保留全部必要条件/例外的题数/需要条件题数 | ≥95% |
| 固定P0联合误放 | 程序保护+Judge最终发布的固定危险候选数 | 0 |

分别报告Judge单独结果与联合发布结果。程序阻断不能掩盖Judge错误允许；Judge拒绝也不能证明程序权限正确。

分别记录JSON解析、严格schema、引用身份/segment绑定和语义判定。不能用一个schema_valid字段混合所有失败。

零论断、空回复、缺输出和全部拒答不能获得100%支持率；无论断的候选按行为与有效回答指标判断。失败/超时不从分母剔除。

### 7.4 多轮任务

- 封存40任务总体正确处理率≥90%。
- 标记为可实际完成的任务子集，其目标终态完成率≥90%；正确拒绝不混入实际申请完成率。
- 每个任务同时核对回复、工具次数/参数、SQL终态、Action确认、审计和不应发生的操作。
- 未满足条件时正确补问/拒绝单独计正确处理；多余工单、额外退款或无依据人工请求使该任务失败。
- 同一初始数据下分别验证顺畅、断线恢复和依赖故障变体；成功不能仅依赖最终文字。
- 用户等待时间与系统处理时间分别记录；模型预算与每轮上限一致。

### 7.5 统计规则

所有门槛使用未四舍五入数值；报告原始分子/分母、点估计、Wilson 95%区间与分层结果。小样本通过只声明该样本集，不声称总体错误率已被证明低于阈值。

若要对总体错误率上限作正式统计声明，必须事前规定置信上界和所需样本，不能只看点估计。重试、修复和同语义多变体不当作独立样本扩充分母。

## 8. 性能与容量档位

### 8.1 声明档位

| 档位 | 环境与最小负载 | 目标/用途 |
| --- | --- | --- |
| P-Demo | 声明8GB GPU配置、真实检索/SQL，LLM可替身；C1至少200次 | 完成率≥98%，演示可重复；不能宣传并发容量或真实LLM端到端速度 |
| P-Engineering | 同一候选真实依赖/本地模型；C3闭环至少300次，另0.5请求/秒至少600次 | 两组完成率各≥99%；拒绝/超时/未知全部计未完成；质量门槛同时保持 |
| P-Overload | 1及2请求/秒各至少60秒，冻结最大队列 | 不要求全部完成，但明确拒绝、有界内存/队列/槽，零重复或越权写；用于背压验证 |
| P-RealModel | 同一Provider与预算，至少100条正式真实模型消息，分三类主要路径 | 满足下表延迟并报告质量/费用；额度不足BLOCKED，不能用替身补齐 |
| P-Soak | 工程档位下0.5请求/秒持续60分钟，至少1800请求，含后台索引竞争 | 完成率≥99%；零关键事实错误/重复业务；资源无持续泄漏，后台有明确进展 |

C1/C3表示同时在途用户请求数，不表示GPU实际并行推理数。固定到达负载不等待上一条完成；闭环与open-loop结果分开，不能相互替代。

P-Demo/P-Engineering/P-Overload/P-Soak默认使用真实SQL/Redis/Milvus及本地Embedding/Reranker，聊天生成与Judge使用契约一致的替身，不派发付费请求；如启用本地理解模型需单独声明资源。其通过不能宣传真实云端LLM端到端并发。需要真实云端模型时按P-RealModel另冻结预算和结果，不能混报。

### 8.2 延迟目标

| 路径/观测点 | P95目标 | 口径 |
| --- | --- | --- |
| API接受并登记Run | ≤800ms | 从服务器接收有效请求到提交接受状态；本地同机测试 |
| 持久阶段事件发送 | ≤300ms | 从事件SQL提交到订阅客户端收到；本地同机 |
| 模板/无模型短回复完成 | ≤800ms | 包括Run管理、校验和最终提交 |
| 本地业务只读查询完成 | ≤1500ms | 无外部慢业务系统、包括持久化 |
| 本地完整冷检索（无付费生成） | ≤3500ms | 包括快照、排队、Embedding、融合和重排；固定候选/文本长度 |
| 已验证缓存回复完成 | ≤800ms | 明确缓存命中，不算模型速度 |
| 真实模型知识问答 | ≤20秒 | 包括理解、检索、生成、Judge、排队和提交 |
| 真实模型复杂单轮诊断 | ≤30秒 | 不含用户思考等待；不超过Run硬期限 |
| 历史重排门槛 | ≤2000ms，独立保留 | 新整体档位不得覆盖历史M5的既有未通过结论 |

所有路径均记录完整分布P50/P95/P99及最大值、超时、拒绝、未知和实际完成数。未完成请求保留真实终止耗时并在总分母计失败；成功请求延迟另列，不能只报成功样本。

### 8.3 公平比较与资源检查

- 固定语料、候选数量、文本长度、唯一语义比例、模型revision、量化、精度、调度、硬件和缓存条件。
- 冷启动/冷索引/热索引/答案缓存分别测试，不能混成一个P95。
- 本地GPU采用采样显存及必要OOM日志；采样峰值不能声称驱动级绝对峰值。
- 10分钟预热后固定有界上下文/缓存负载，结束RSS不高于预热基线的1.2倍，且无持续上升趋势；增长原因必须解释。
- 文件描述符、TCP连接、模型客户端、租约、活动槽、未完成线程与队列有上限；结束时全部可核对。
- HTTP超时不代表服务端GPU已停止；不能立即释放资格并假装旧推理不存在。
- 至少一次前后台公平性验证：后台索引完成或明确重试/终止，旧发布指针保持。
- 采用候选优化前质量不退化；实验应记录ABA或同条件重复，不能仅凭一次串行更快作因果结论。

## 9. 费用与真实调用授权

原M4 660/660、M5 v1 1027/1027、Judge v2 256/256额度均已使用完，当前可复用余额为0。

本规范的数据规模与性能档位不是派发授权。每次L3/P-RealModel计划必须：
1. 冻结Provider、模型、用途、数据和源代码。
2. 计算最大HTTP尝试数，包含理解修复、规划、生成、Judge、备用与必要契约冒烟。
3. 冻结输入保守预留、输出上限、币种/费率来源及未知项。
4. 获得本计划具体额度后建立固定授权文件与dispatch账本。
5. 先做最多6次受控冒烟，契约/绑定/预期异常则停止后续批量。
6. 缺少余额、原账本变化、源码漂移或调用结果未知时按原操作恢复规则处理。
7. 不通过换目录、删账本、重启或隐藏SDK重试扩大预算。
8. 额度不足可分批冻结计划，未完成总体集保持PARTIAL进度/NOT_RUN总体门禁，不拼凑PASS。

账单未核对时只报告按配置估算费用；真实usage与预留分别记录，未知usage不补0。费用对账不能泄漏密钥或账户完整信息。

## 10. 证据包规范

推荐目录为reports/optimization-v2/<release_candidate>/<run_id>/，实际创建前检查.gitignore，禁止提交数据库、原始敏感日志或凭据。

每个正式证据包至少包含：
- manifest.json：目标AC2、环境层次、开始/结束时间、源码/配置/数据/模型/依赖hash、资源owner、命令与退出码。
- source-start/source-end及比较：覆盖相关生产与评测源码、配置模板、schema、数据和标签。
- case-results：case_id、预期、实际、安全错误码、状态、各尝试与耗时、工具/事件/回执引用。
- metrics：分子/分母、分层、区间、失败/超时/unknown、资源和成本口径。
- SQL/事件/工具审计的脱敏快照；必要浏览器截图或录屏与构建hash。
- model-ledger/dispatch审计与旧账本hash（只读核对）；未知操作清单。
- human-review记录与争议裁决；不能只保存模型给的总分。
- errors-and-limits：失败、来源漂移、未运行项和不能推广的范围。
- cleanup-summary：测试资源保留/清理、原资源/账本未变化、未完成Job/槽的最终核对。

原始草稿/判决仅在必要评测场景分级、脱敏、加密、限期保存，用于定位绑定失败；一般业务Trace不保存完整用户内容或隐藏推理。未保存导致无法定位时如实写明，不编造“已离线复现”。

| SQL | 预留失败、事务回滚、连接池耗尽 | 无无账派发/未提交正文，unknown边界准确 | AC2-13-003、AC2-14-006 |
| Worker领取 | 两Worker同刻领取、旧token续租 | 仅当前owner可推进，旧owner不复活 | AC2-10-003 |
| 只读工具 | 超时、错误数据、取消后迟到 | 有界失败，不串资源，迟到不成为当前事实 | AC2-03-005、AC2-05-007 |
| 写工具 | 服务端提交后客户端超时 | 先查回执，无盲重发 | AC2-04-008 |
| 模型出口 | 429/500/无usage/已发送unknown | 尝试与费用上限不绕过，unknown不补0 | AC2-13-004、AC2-13-005 |
| Judge | schema非法、引用错、绑定错、超时 | 细分原因，不发布候选，不无界修复 | AC2-08-004、AC2-08-005 |
| 检索 | Embedding/Milvus/Reranker单独故障 | 正确降级，元数据真实，busy不污染缓存 | AC2-07-005 |
| 发布期间 | 知识撤销、policy更新、权限撤销 | 旧证据/旧资格失效，无迟到发布或提交 | AC2-07-007、AC2-04-006 |
| 本地GPU | 队列饱和、OOM、线程不能及时停止 | 明确拒绝/超时，资源有界，不靠吞请求过关 | AC2-13-007、AC2-13-008 |
| 事件通道 | 断线、重复、乱序、慢客户端 | 可补读，正文与动作不重复，不阻塞提交 | AC2-10-008、AC2-10-010 |
| 通知 | 供应商返回未知或重复消费 | 对账与幂等，模拟/真实状态不混淆 | AC2-10-011 |
| 文件/索引 | 上传解析失败、Job重复、迟到成功 | 原发布版保留，撤销不复活，资源受控 | AC2-06-002、AC2-06-006 |
| 观测 | Trace/日志服务不可用 | 业务不被遥测故障改变，队列不无限增长 | AC2-16-006 |
| 迁移/回填 | 运行中断、重复重启、旧新版本混用 | 不丢历史、不重复动作、可恢复回填 | AC2-14-003、AC2-14-004 |
| 恢复环境 | 缺对象存储/索引/密钥配置 | 明确恢复范围与不足，不把SQL能启动当全量恢复 | AC2-17-004 |

每个故障至少记录注入时刻、进程/线程/网络位置、实际派发次数、SQL前后、公共事件与资源收尾。不能通过删掉反例或把故障夹具改成正常结果使测试变绿。

## 16. 发布分级与通过规则

### 16.1 三种声明

| 声明 | 必需条件 | 对外可说明 |
| --- | --- | --- |
| 已实现/局部验证 | 对应L0/L1/L2等实际证据 | 精确说明实现内容及测试范围；可用于简历，但保留未验限制 |
| 工程候选准入 | 本期范围P0/P1全部通过，所需L2/L3/L4/L5/H齐全，P-Engineering达标 | 该候选、环境与能力范围通过；不代表所有生产条件 |
| 生产部署验收 | 工程候选+真实部署安全/监控/备份恢复/回滚/运维与声明外部服务实测 | 仅对实际部署和已接入能力作承诺 |

模拟退款、通知或人工连接即使部署在线，也必须继续标模拟或未接入，不能由“生产部署”四字推定真实支付/通知能力。

### 16.2 汇总规则

- 同一发布范围内全部适用P0和P1通过才能整体PASS；BLOCKED、NOT_RUN、INVALID_EVIDENCE均不得当作通过。
- P2允许明确延期；取消P1范围必须在实施/测试前版本化说明，不能观察失败后移除。
- 一个P0成功模板不能抵消同组越权/重复写反例。
- 跨模型、跨数据、跨代码、跨硬件的最佳结果不能拼成一个候选的整体成功。
- 所有真实质量与性能结果必须绑定同一发布候选和配置；必要部分复验需说明继承证据的依赖边界。
- 发布矩阵列每个AC2实际状态/证据；空白默认NOT_RUN。
- 最终由验收负责人确认范围与证据；编写代码或文档的模型不能自行宣称独立人工验收完成。

### 16.3 备份与回滚目标

首个本地工程候选的恢复目标：演练RTO≤30分钟，RPO≤24小时，并记录实际备份截止点与丢失数据条数。若模型下载/外部服务恢复不在目标内必须单列，不隐去总不可用时间。

备份恢复到另一隔离环境，逐项核对订单、申请、消息、Run/Task、知识发布指针/epoch、必要对象及模型账本。恢复后的未知动作先对账；不能恢复旧账本后重复使用已消耗外部额度。

业务需要更严格RPO/RTO或跨机部署时另冻结生产目标，不将本地演练值推广为生产保证。
