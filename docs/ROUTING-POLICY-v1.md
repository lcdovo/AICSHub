# 路由策略收拢（2026-11-06）

## 职责

`app/agent/intent.py`提供主题候选及置信度，保留规则优先与既有LLM兜底。
`app/agent/routing_policy.py`是普通业务分流、补槽要求及意图目标映射的共同策略入口。
`RoutingNode`仅负责提取/合并当前业务参数、调用策略并投影`RouteDecision`，不再独立维护退款/投诉词表。

`TopicPolicy`集中声明每个主题的目标节点、咨询词、办理词和必需参数；`RouteDecision`返回目标、原因、缺失参数及可选澄清文本。策略是无模型/存储/工具副作用的纯组件，可独立注入。
旧`is_refund_inquiry`、`is_complaint_inquiry`、`required_slots`、`intent_destination`及Graph私有方法保留兼容转发；不另维护一份规则。内部`RoutingDependencies`从五个回调缩为参数提取器和一个策略组件。

## 决策优先级

1. 影子模式仍在确认/取消前终止；有效退款确认/取消仍由原入口处理，不向模型索取确认。
2. 模型模式沿用严格`RequestUnderstanding`、实体来源和条件校验。其已验证`request_type`进入普通路由时不再被旧咨询关键词覆盖；模型的澄清、条件先读及只读计划仍由原适配器处理。
3. 规则模式在当前语句中区分咨询与办理。明确的非疑问、非否定办理分句优先；同句中询问申请材料/流程不因包含“申请/提交”自动视为办理。订单号仅为业务参数，不能把政策咨询升级成写操作。
4. 识别到否定的人工请求不进入人工节点。规则模式中识别到条件性退款/投诉办理时先澄清，不自动生成申请；候选模型模式的条件先查询行为保留。
5. 确定需要业务执行后才检查必需参数：订单查询要求订单号，退款还要求至少6字符的原因。
6. 寒暄走模板，其余general问题走知识检索；其他主题依据统一目标映射路由。

咨询路由清空旧缺参列表，防止已转知识问答但仍被响应节点误当补槽流程。
历史工具只对识别到的延续性回复提供主题背景，不再覆盖任意新问题。延续句式集中在同一策略模块。
规则路由和模型理解语义校验共用按主题的`action_is_negated`，避免两处否定词规则各自漂移。

## 边界与未验证范围

有限词表和中文分句规则不等于通用语义理解；混合、多义或未覆盖表达仍可能误路由。这里没有替换主题分类器，也没有将候选统一理解切为默认。
退款预览、明确确认、领域权限、幂等及SQL/Redis租约机制不由路由判定替代。路由进入工具节点不代表已获执行授权。
业务配置仍保留rules/灰度0；不修改模型、RAG、Judge或供应商预算。本次不引入付费调用，不宣称M4/M5质量门槛、真实依赖、浏览器或生产验收通过。
