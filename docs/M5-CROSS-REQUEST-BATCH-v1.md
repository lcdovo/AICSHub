# M5有界跨请求批处理候选 v1

2026-11-04。默认仍为`LOCAL_MODEL_COORDINATOR=process`；业务路由、模型、知识空间与原质量/性能门槛不变。新增`batch`仅供单API进程隔离实验，不替代Redis跨worker协调。当前结论：功能回归通过，200有限压力完成率通过，但并发10重排P95超过2000ms，容量仍FAIL，不进入M6或启用业务候选。

## 实现与边界

- 整轮独立Permit最多10个，额外入口等待者最多2个；前台入口等待500ms、后台50ms，整轮上限10秒、HTTP/阶段原5秒截止不重置。后台最多占1个整轮资格。身份、deadline与在途引用仍逐请求保存，释放自己的资格不会释放其他请求。
- APIEmbedding实例内按同一端点/模型/维度合并请求，窗口3ms、最多20个输入、最多10个未归还请求，无后台线程池或共享答案缓存。返回向量先校验数量、唯一index、维度与有限数，再按各自偏移拆分；不同实例不拼接。超过20条的后台输入继续分批，保留尾部。
- 模型通道独立：Embedding最多1个批次HTTP，重排最多2个HTTP。FIFO与每4次前台后优先后台共同约束等待；通道队列最多10个，全部计入调用原截止。重排保持各查询完整候选列表，不把多用户文本拼成同一个rerank query；没有新增多查询rerank协议，也不声称自实现GPU张量批处理。
- 通道等待结束、实际HTTP发送前重新校验批次所有成员；成员已过期/取消/失效则保守拒绝整个尚未发出的批次，不自动重试或直调。HTTP返回后每个成员再独立检查，失效成员的结果不进入其缓存；其他有效成员可获得自己的结果。
- 调用方退出或超时不强杀GPU；已发HTTP归还前仍保留引用和整轮资格。关闭服务拒绝/唤醒排队者，已借出的连接池在归还后关闭。多worker配置直接拒绝候选；两个分别配置WORKERS=1的独立进程仍不能互相协调，部署者必须保证仅一个参与进程。
- 有界准入10个请求意味着更多请求可在原5秒阶段内等待；入口500ms未改不代表整个请求只排队500ms。完成率增加不能解释成GPU吞吐或原延迟门槛已经提高。候选模型仍运行于本机同一RTX4060，独立通道也不代表独立物理GPU。

实现：`app/services/local_batching.py`、`local_admission.py`、`embedding_service.py`及配置schema；缓存身份已有coordinator模式和版本，隔离旧模式结果。模板仅说明候选，不修改业务`.env`。
