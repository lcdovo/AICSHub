# 退款原因追问与明确长句确认（2026-11-08）

## 行为与范围

本轮落实“下一步：原因不足定向追问、长句确认／取消契约”，仅修改工作区与完成离线验收，不部署、不调用真实供应商。现有原因至少6字的要求保留；单项退款任务缺少合格原因时，程序安排ask_user/reason，明确请用户按实际情况补充，不再多调用规划模型选择转人工，也不创建预览或申请。收到补充原因后仍重新查单、检索和核验。

长句采用有限整句白名单，允许首尾空白及至多一个句末句号/感叹号；不删除句内文字，不做关键词匹配、不让模型授予确认。原短词CONFIRMATIONS保持不变。

| 输入 | 行为 |
| --- | --- |
| 确认提交这笔退货退款申请。 | 仅确认当前退货退款预览 |
| 我确认提交本次退货退款申请！ | 仅确认当前退货退款预览 |
| 确认提交这笔退款申请 | 确认当前仅退款/退货退款预览，不能确认换货 |
| 取消刚才的申请，不要提交。 | 取消当前待确认预览，申请数不变 |
| 取消本次退款申请。 | 同上 |
| 不要提交这笔退货退款申请。 | 同上 |
| 如果……确认、他说“确认……”、之前确认……、确认……吗？ | 不作为提交授权 |
| 确认并换订单/修改金额/附加其他操作 | 不作为提交授权 |

上述“识别确认”不是独立授权凭据：仍须有效预览、本轮持久化用户消息、可信主体、相同会话/订单/参数/动作版本、领域资格、租约及幂等校验。聊天节点、轮次记录、SQL最终提交及提交后恢复共用同一识别函数；SQL读取实际Message正文，不采信模型或调用方宣称已确认。类型不一致时拒绝提交，不改写预览参数。

取消同样只作用于当前已绑定的预览。已提交申请不能作为预览取消。默认不会把任意包含“确认/取消”的句子解释为授权；白名单之外仍走现有理解/澄清路径，不代表已支持所有中文表达。

- app/services/refund_application.py、run_execution.py：SQL提交和既有回执恢复复用同一契约，恢复不重新提交。
- app/agent/task_loop.py：单项申请缺原因时确定补问；多项编排和其余业务门槛未扩展。
- tests/test_refund_language_contract.py：整句、类型、反例、SQL最终校验，以及REST/WS三轮流程。
- tests/test_m2_runs.py：短词及长句确认的提交后崩溃恢复、回执损坏、重复恢复不重复登记。

原供应商捕获与付费失败记录保留。历史回放测试改为验证新源码会在旧search/handoff回包消费前补问，明确保留未使用的旧回包；不能把旧付费结果追写为修复通过。
