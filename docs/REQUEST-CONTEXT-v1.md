# 请求理解与必要上下文优化 v1

日期：2026-11-06。对应优化开发方案DEV-02/DEV-09的局部实现；不是N1整体或M4/M5质量通过。

## 本次改动

1. **统一理解输入**：新增`app/agent/request_context.py`，以不可变`RequestContext`组织当前消息、必要历史、已知订单及未完成主题。规则分类、模型分类兜底和候选结构化理解复用选择与长度限制。
2. **必要历史**：仅对指代/追问或未完成补参选择背景；独立问题和明确换订单不附带旧订单。最近窗口最多7条，每条最多600字符，历史合计最多2400字符；仅发送user/assistant的role/content，不携带工具回包、system消息或额外元数据。只移除尾部本轮用户消息一次，不删除其他相同历史。当前消息不截断，输入上限仍由原HTTP/模型网关约束。
3. **一致校验**：结构化理解在调用前冻结上下文，修复与结果来源校验使用同一快照；不能在await之后重建可变历史来证明模型实体。用户摘要、旧工具事实和记忆不作为本轮确认或当前订单状态证据。
4. **主题/行为/情绪分开**：规则识别单独记录有限情绪观察；明确维修/连接等技术咨询不会仅因负面词走投诉。普通路由记录`ActionIntent`中的咨询/查询/办理/澄清，`executable`仍为false，不能授权业务。
5. **不比较两种置信度**：模型分类输出须通过严格枚举、bool、有限数值和extra字段校验。合法且不冲突的修正可采用，自报分数仅作观察；无当前办理表达/咨询依据却分类为退款、投诉、人工时补问，不能靠0.99分覆盖。Provider异常保守说明；取消继续向上传播。
6. **歧义先补问**：规则路径遇到多个订单或未提供新订单号的“另一个订单”先询问，并清除本轮默认订单选择；不删除SQL历史动作。候选模型路径保留经实际可见来源校验后的明确订单选择。
7. **多轮补参**：`for_next_turn()`保留未完成`missing_slots`，仍清空证据、工具与确认等本轮产物。待补退款原因的简短回答延续原办理意图，内容通过原业务参数契约进入原因字段；不因“包装”等原因词被改判成政策咨询。新问题仍重新识别。
8. **避免隐式写入**：历史意图升级仅记录建议，不直接设置人工请求；规则路径缺乏明确投诉/人工办理表达时先澄清。人工澄清话术不再声称“正在转接”。结构化理解拒绝把明确咨询/技术问题或被遗漏条件升级成直接申请。

## 保留的边界

- 确认/取消仍在普通理解前结合有效预览处理；shadow仍先拦截，不执行建议动作。
- 退款权限、资格、预览版本、本轮确认、SQL幂等及租约仍由原服务强制，分类和`ActionIntent`不是授权。
- 业务.env未修改，仍为rules/灰度0；未把模型统一理解切为默认，未切换供应商或增加真实评测调用。
- 当前条件请求：规则模式仍先提示核实/澄清；候选结构化理解可先只读查单。未新增“自动完成条件退款”的执行流程。
- 来源/否定/技术咨询/换对象保护仍是有限中文规则，不证明任意表达的理解准确率。保守补问可能增加，需真实留出集评测后校准。
- 这里只统一请求理解上下文；回答生成、检索改写、长期记忆的完整重构尚未实施。未新增持久Task表或通用记忆平台。
- 新增契约校验和提示已改变候选输入，旧模型质量报告不能当本版本真实复验结果；M4/M5失败状态和费用账本保持。
