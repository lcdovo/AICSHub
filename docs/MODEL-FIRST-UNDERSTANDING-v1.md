## 目标与当前状态

将候选`model`路径整理成三个清楚的职责：

```text
确认 / 取消 / 完整确定寒暄 → 程序快捷处理
其他请求 → 一份结构化模型理解 → 来源与冲突检查
         → 程序检查参数、选择允许步骤 → 原业务服务鉴权、预览、确认与执行
```

旧`rules`模式保留为独立兼容/回退配置。候选模型理解失败时不会自动进入旧规则或旧`classify_intent`，避免两套分类器竞争或失败时升级为写操作。

本次没有把真实业务默认改为模型。当前统一理解候选的真实质量尚未重新验收，且历史M4/M5/Judge评测额度已耗尽；按先前约定，完成具体真实评测和准入后再切默认，而非用替身通过代替模型效果。

## 本次实现

### 1. 确定事件入口

新增`app/agent/request_events.py`作为寒暄词表和完整匹配的共同入口。`IntentNode`和响应模板共用它，避免“你好，帮我查订单”“谢谢，申请退款”等整句被问候前缀截走；英文`hi`也不再任意匹配其他单词的子串。

有效退款预览的明确确认/取消继续先处理；确定寒暄直接生成流程结果，不解析模型工厂或规则分类器。shadow仍在确认/取消前拦截，只记录观察，不执行业务。

### 2. 一份结构化理解

复用`RequestUnderstanding`的主题、请求类型、实体、条件、子诉求、情绪、服务偏好、补问与检索查询，新增兼容可选字段：

| 字段 | 内容 | 程序约束 |
| --- | --- | --- |
| parameters.reason | 从可见文本提取的申请原因 | 必须在实际模型可见的当前消息或必要历史中出现；不能由程序把整句申请自动当成原因，提交前仍核对预览 |
| parameters.refund_type | refund/return/exchange或null | 严格枚举；真正资格与支持范围仍由领域服务核实 |
| parameters.complaint_content | 已明确投诉的正文 | 严格字段和文本来源，不包含身份、权限或确认 |
| missing_information | order_id/reason/product/request | 有界枚举，程序结合业务必需参数决定补问 |

旧输出可不提供新增字段，默认空值。但缺少退款原因时进入补参，不能为了兼容补造原因。旧投诉输出未提取正文时，只允许将已理解为`complaint/apply`的当前原话作为投诉内容，不能当作退款原因、权限或执行证明。

提示词明确区分咨询、查询、办理、情绪和前置条件；模型自报置信度不参与这条路径。结构非法或来源/冲突校验失败最多修复一次；Provider异常返回不可用，取消继续传播，无隐式旧分类兜底。

### 3. 程序决定允许步骤

`RoutingPolicy.decide_structured()`只读取主题、请求类型、类型化参数和缺失项，不接收原话，不运行咨询/动作关键词选择。

| 模型理解结果 | 程序允许的步骤 |
| --- | --- |
| inquiry | 使用本轮检索查询进入RAG |
| query_order/query | 有订单则进入受保护只读查询，否则补订单号 |
| 合法read_tasks | 最多两个登记只读任务，实际身份/权限仍独立校验 |
| refund/apply | 核对订单、原因等参数后进入预览；未确认不提交 |
| complaint/apply | 使用已选正文进入原工单服务，保留当前消息授权与SQL幂等 |
| human/apply | 进入原人工请求服务，不能把登记说成实际接通 |
| cancel但无有效待确认动作 | 说明无法核实可取消对象并补问，不再检索取消政策或创建新动作 |
| change或不支持的topic/apply | 明确澄清，不猜测工具或执行任意变更 |
| product/request缺失 | 补充关键对象或诉求，不由关键词自动选择 |

路由节点和工具节点在模型路径不再调用旧regex提参。工具执行前再次核对语义契约、选定订单、显式参数和允许目标，不能把后续变化的原因或订单偷偷用于预览。

### 4. 理解与上下文绑定

将调用前冻结的`RequestContext`保存为本轮`understanding_context`，后续路由和工具复核使用同一快照，不因路由清理缺参或历史变化重新选择证据。

快照以user/actor/session/source_message/current_message摘要绑定本轮scope，身份、消息或来源变化后拒绝继续。快照只保留必要历史、已知订单、未完成主题和待补参数，不把旧确认、工具回执或系统消息当作授权。

下一轮不继承`understanding`和`understanding_context`。条件、参数、预览和业务回执仍分别受原类型与领域检查约束；上下文摘要不是业务授权令牌。

### 5. 检索与确认保护

模型理解给出的检索查询直接通过`record_query_rewrite`记录，避免重复改写并绑定本轮scope。

条件诉求继续先只读核实；本片未新增自动条件退款执行器。原退款业务对订单状态、资格、金额、类型及本轮确认的限制保持，例如“没发货就退款”不能单凭语言理解覆盖当前退款资格规则。前置查询成功不等于资格满足、申请已准备或已提交。

## 配置与准入

- 业务`.env`未修改，默认仍为rules、灰度0。
- `.env.example`补齐显式安全默认和候选说明，不自动开放模型流量。
- 后续启用需要明确`REQUEST_UNDERSTANDING_MODE=model`、准入后的灰度比例及新`REQUEST_UNDERSTANDING_VERSION`（例如`understanding.model-first.v2`）。这只是配置说明，不是本轮启用动作或付费授权。
- 接受Run时固定模式与策略版本的原机制保留；不能通过运行中改开关改变已接受消息的行为。
- 真实模型需要验证新增schema、来源、补参、多诉求、条件和拒绝行为。旧质量报告不适用于新增契约；独立数据/真实模型证据不足时保持候选。

## 未验证与限制

真实Provider新增schema兼容、真实语言理解准确率、误补问率、成本、容量与部署尚未复验。离线模型回包是显式夹具，不代表模型自己理解正确。既有有限中文来源/否定/条件冲突保护继续作为安全边界，不代表通用语义证明。

实体仍沿用原`entity_source`契约；跨当前消息/历史的混合来源表达可能需要补问。文本出现在必要历史只证明模型看得到，不证明它是当前业务事实或用户已确认的操作；关键业务状态仍由服务重新核实。

本片没有增加自治Agent、模型切换或付费调用，没有重置旧账本，没有修改业务数据库、知识数据、容器或模型缓存，也没有移除原业务确认、权限、幂等和租约检查。
