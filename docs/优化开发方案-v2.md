## 2. 问题诊断与设计取舍

| 问题 | 影响 | 本轮重构方向 |
| --- | --- | --- |
| 主题、情绪、操作意图混合 | 负面评价可能变成投诉办理，咨询可能进入补槽或申请 | 统一任务理解，情绪单列，程序决定行动资格 |
| 两种置信度直接比较 | 不同量纲的数字产生不可靠覆盖 | 合法性、实体来源、冲突规则、澄清与评测准入 |
| 静态主题路由难处理多步任务 | 排障、查单、售后之间难自然接续 | 有限自主只读决策与确定写流程结合 |
| 状态与兼容字典多份表示 | 跨轮污染、恢复偏差、修改牵连 | 领域事实/任务/轮次/派生观察分层，逐键退役 |
| 响应节点承担过多职责 | 难定位生成、校验、缓存和发布问题 | 构建、审查、发布三个独立组件 |
| Judge与生成可复用同模型 | 共同误判；契约绑定失败掩盖可用性问题 | 程序硬规则+独立调用+人工评测，保留未知原因 |
| 冷BM25与SQL快照开销 | 知识增长时重复构建；权限扩展困难 | 版本/空间隔离的只读索引快照与有界增量刷新 |
| 进程内聊天任务 | API退出后不能直接继续执行一般任务 | SQL任务领取、检查点、未知动作对账 |
| 流式协议与实际发送脱节 | 节点事件已记录但路由集中等待，用户无进度感 | 持久阶段事件及时发送，正文审查提交后发布 |
| 人工页面与真实协作闭环不完整 | 接续信息丢失、目录或负载多源 | SQL任务归属、接续包、明确坐席角色与审计 |
| 评测来源与标签质量混杂 | 合成/替身通过被误当真实能力 | 冻结数据、独立人工复核、分层报告与真实状态验证 |
| 工程展示缺少统一主线 | 功能多但难说明解决的问题 | 三条可演示业务闭环与三类岗位证据 |

## 3. 产品目标与范围

### 3.1 定位

“面向智能设备售后的、可恢复、可审计、支持人工接续的客服Agent平台”。

第一轮选耳机、打印机、投影仪三类产品建立完整资料和业务夹具；具体型号与政策由N0冻结。其他产品继续明确适用范围，不为了覆盖数量编造手册、政策或服务能力。

### 3.2 用户与角色

| 角色 | 主要任务 | 目标可见范围 |
| --- | --- | --- |
| 客户user | 咨询、排障、查询自己的订单、确认售后、查看进度 | 自己的会话与业务；获准知识空间 |
| 坐席support（拟新增） | 领取/处理授权工单、人工接续、补充处理记录 | 已分配或允许领取的队列；禁止任意浏览所有客户 |
| 管理员admin | 发布知识/政策、管理坐席、查看系统与评测 | 管理范围，敏感操作审计 |
| 后台worker | 索引、摘要、通知、Run恢复与对账 | 固定任务服务身份和最小操作权限 |

当前UserRole只有user/admin；support身份、会话授权和坐席绑定必须真实实施，不能仅隐藏菜单。

### 3.3 三条业务闭环

| 场景 | 必须完成的过程 | 正确终态 |
| --- | --- | --- |
| 故障诊断 | 识别型号/现象→确认必要环境→检索→指导一步→接收用户反馈→调整或转人工 | 已解决、等待反馈、材料不足或明确升级 |
| 售后申请 | 查订单→政策与资格核实→显示依据/金额/类型/模拟标记→用户明确确认→提交→读取回执 | 已登记申请、等待确认、资格不符、取消或结果未知 |
| 人工接续 | 整理目标/事实/尝试/未完成事项→创建真实人工请求→分配→接续处理→解决/退回 | 每个状态有SQL记录；未实际连接时不承诺已接通 |

### 3.4 本轮范围和延期事项

P0/P1范围覆盖三条闭环、可恢复执行、证据回答、客户/坐席/管理界面、模型治理、质量与部署验证。

以下仅作扩展项，需独立价值与验收后再纳入：真实支付/短信/邮件供应商、多组织租户计费、语音客服、图片视频诊断、任意互联网浏览、任意代码执行、多个自治Agent相互委托、跨地区高可用和自动扩容。外部接口未接入时保持明确模拟标识。

## 4. 目标架构

### 4.1 模块化单体与独立Worker

~~~mermaid
flowchart TB
    UI[客户/坐席/管理Web] --> API[FastAPI API与事件订阅]
    API --> AUTH[身份/权限/幂等/接受Run]
    AUTH --> SQL[(MySQL权威事实)]
    WORKER[独立聊天与后台Worker] --> SQL
    WORKER --> RT[Agent Runtime / LangGraph]
    RT --> CTX[上下文构建与任务理解]
    RT --> PLAN[有界下一步决策]
    PLAN --> READ[只读工具与RAG]
    PLAN --> ACTION[业务策略/预览/确认/执行]
    READ --> ANSWER[回答构建与证据审查]
    ACTION --> ANSWER
    ANSWER --> PUB[结果提交与发布]
    PUB --> SQL
    SQL --> EVENTS[持久事件读取]
    EVENTS --> API
    READ --> IDX[知识索引与Milvus]
    RT --> GW[模型网关/预算/出口]
    WORKER --> CACHE[Redis协调/缓存/通知提示]
~~~

原则：SQL存事实和任务生命周期；Redis不作为唯一成功凭据。Milvus是派生索引，发布版本由SQL控制。MCP是接入协议，业务授权属于服务端领域服务。

## 5. 核心契约与事实来源

### 5.1 契约清单（拟逐步扩展）

| 契约 | 关键内容 | 权威来源/限制 |
| --- | --- | --- |
| PrincipalScope | actor、owner、session、role、授权知识空间、Run | 服务端认证与数据库；模型和工具回包不能覆盖 |
| TurnContext | 当前消息、相关历史、摘要版本、上下文选择说明 | 不可变本轮快照；背景不等于证据 |
| TaskUnderstanding v2 | 目标、主题、request_kind、实体来源、条件、子诉求、缺失信息、情绪 | 模型建议通过程序校验后使用 |
| TaskRecord / TaskStep | 跨轮目标、当前步骤、依赖、已尝试方案、待确认动作 | SQL任务事实；一个Task可包含多个Run |
| NextStepDecision | answer/clarify/retrieve/read_tool/prepare_action/handoff/finish | 枚举及允许动作；禁止任意代码、SQL、身份 |
| ToolSpec / ToolInvocation | 严格输入输出、风险、权限、超时、幂等及版本 | 受信工具注册表；结果为不可信数据 |
| PolicyDecision | eligible/ineligible/needs_info/unknown、命中规则、版本、有效期 | 程序规则与当前业务快照；不凭模型分数 |
| ActionProposal | 参数、精确金额、资源、预览版本、到期、模拟标记 | 领域服务生成；UI展示不授权 |
| EvidenceBundle v2 | 片段/回执身份、版本、适用范围、hash、缺口、矛盾 | 当前发布快照/本轮授权回执 |
| DraftCandidate | 正文、候选hash、来源、结构化事实声明 | 私有草稿，不直接发给前端 |
| ReviewDecision | 可回答性、回复行为、有效性、错误码、证据hash | 程序硬约束与独立审查联合决定 |
| PublishedResult | message_id、run_id、最终正文hash、回执引用、提交时间 | 仅SQL提交后可发布 |
| MemoryEntry | 用户陈述/偏好、来源消息、版本、有效期、删除状态 | 背景信息，不能替代权限或当前业务事实 |
| PublicRunEvent | event_version、run_id、sequence、type、有限payload | 服务器生成；不泄漏内部提示、草稿或隐藏推理 |

### 5.2 四种生命周期

1. 领域事实：订单、申请、工单、发布知识、策略版本、操作审计，存SQL。
2. 跨轮任务：TaskRecord、任务步骤、待用户补参或确认，存SQL。
3. 本轮快照：输入、证据、草稿、审查、调用观察，本轮建立，本轮失效。
4. 可重建投影：Redis状态、检索缓存、UI进度、索引，带版本并可从事实恢复。

### 5.3 Run、Task、Action分别建模

- Run表示一条被接受消息的执行。返回追问或确认预览时，本轮完成相应输出。
- Task表示跨轮业务目标，可处于active/waiting_user/waiting_confirmation/waiting_human/completed/cancelled/failed。
- Action表示明确业务动作，沿用RefundAction等领域记录及其版本/幂等。
- 下一条“确认”创建新的Run，绑定原Action最新版本；不能重启旧Run并借用历史确认。
- 传输断开不等于取消任务；取消Task不等于撤销已提交领域动作，必须明确可取消边界。

Run冻结执行算法、模型/提示/schema和预算策略版本，不把订单状态、资源权限、知识发布状态或售后资格永久冻结。写入前仍核实当前业务事实；规则被撤销或资格变化时旧预览失效。策略快照不能成为绕过实时授权的理由。

### 7.2 理解流程

- 可信确认/取消与确定寒暄快捷路径优先。

- 模型不能指定actor、owner、权限、数据库连接或任意工具代码。
- 发现否定、条件、转述、对象冲突、多个订单或未支持操作时使用明确规则或补问。
- 不比较规则换算置信度与模型自报置信度；不确定性记录为具体缺口。
- 合法性修复最多一次，计入总调用预算；不可用时保持只读/补问，不转为未经授权的申请。
- routing_policy.py继续承载确定目标映射和资格前置；候选理解不再被后续旧regex重新选择订单。
- 多诉求记录顺序与依赖；独立只读请求可合并执行，多个写意图分别预览和确认。
- shadow只记录建议和对照，不创建业务动作、写入型人工请求或发布供应商草稿。

保留当前主模型为对照；本地Qwen3-4B-Instruct-2507量化方案仅作为候选，其他模型通过相同数据与Provider契约比较。模型选择依据任务质量、结构合法率、延迟、成本和显存，不依据参数量或发布日期单独决定。

## 8. DEV-03 有界Agent任务执行

**优先级：P0/P1；阶段N4，依赖N1/N2/N3；验收组AC2-03。**

### 8.1 决策与执行

- 模型选择下一项允许步骤，程序生成其可调用能力视图。
- 先验证计划，再执行工具，将结果封装为ToolObservation，再决定继续、补问、回答或等待确认。
- 查询和排障允许有限循环；业务动作进入固定预览/确认/提交子流程。
- 排障保存已尝试步骤与用户反馈，避免重复建议和无依据宣布修复。
- 只接受有结果依赖或理由摘要的有限计划，不存储/展示模型隐藏思维链。
- 相同步骤、相同参数和相同证据连续无进展两次即终止或补问。
- 成功、等待用户、等待人工、资料不足、权限拒绝、依赖不可用、期限耗尽为独立终止原因。
- 模型只能申请人工协助；创建真实人工请求仍由用户诉求、业务策略和服务授权约束。

### 8.2 初始执行预算（提议，N0冻结）

| 项目 | 初始候选上限 | 约束 |
| --- | --- | --- |
| 图技术步数 | 24 | 保留现有最终硬防线 |
| 自主下一步决策 | 3次/Run | 无进展提前终止 |
| 业务只读工具调用 | 4次/Run | 缓存/重复读取也记录，重试次数单列 |
| 独立只读并发 | 最多2路 | 同GPU推理仍服从共享资源预算 |
| 实际模型HTTP尝试 | 最多6次/Run | 理解、修复、规划、生成、Judge、回退共同计数 |
| 单次回答重生成 | 最多1次 | 替换后重新审查，预算不足不得跳过审查 |
| 重新检索 | 最多1轮 | 因明确证据缺口触发，禁止无目的循环 |
| Run总期限 | 候选60秒 | 包括排队、模型、工具、审查及提交前检查 |
| 等待用户确认 | 退出当前执行，持久化等待 | 不占用模型并发槽；动作TTL单独配置 |

全局模型尝试上限优先于各局部上限，不能把局部上限相加当作允许9次以上调用。一个典型知识请求可用“理解/首步合并、生成、Judge”三次；简单模板请求可以零模型调用。内部SDK重试必须关闭或纳入同一尝试账本。

## 12. DEV-07 检索、证据与可回答性

**优先级：P0/P1；阶段N5；验收组AC2-07。**

### 12.1 检索流程

1. 从可信授权范围读取已发布快照与epoch。
2. 结合当前任务选择查询，保留产品/订单/数字/否定及问题对象。
3. 完整问题不改写；上下文不明先补问；有必要时复用理解阶段的检索查询，避免重复模型调用。
4. BM25与dense分别召回，先过滤空间、发布版本和Embedding指纹，再排名。
5. 用RRF融合，保留原始分数及score_type，不把RRF数值与余弦阈值比较。
6. 在独立预算内重排，失败保留融合顺序及明确降级原因。
7. EvidenceAssembler组织片段、FAQ/表头、规则和授权工具回执。
8. EvidenceAssessment记录完整性、矛盾和资料缺口；不能仅凭高排名标supported。
9. 资料不足且存在明确缺口时最多补检索一次，否则补问或有限回答。
10. 生成和审查前复核当前知识版本；变化则拒绝旧证据或重新取证，不缓存旧稿。

### 12.2 冷路径与索引优化

当前BM25按请求快照构建。目标先采用不可变的进程只读BM25快照，键为knowledge_space/epoch/tokenizer_version；同epoch复用，epoch变化单次构建，等待/失败有界。多个worker可各自缓存，但都必须先读取SQL发布epoch。

知识规模超出内存档位后再评估持久全文索引。是否更换检索服务由语料量、更新频率、实际耗时和部署成本决定，不为技术数量引入第二套事实源。

### 12.3 证据契约

每条证据包含evidence_id、kind、document/version/chunk或tool_invocation/receipt标识、content_hash、产品范围、授权scope、有效时间及完整有界内容。

EvidenceAssessment分别记录：
- 对问题：full/partial/unknown/not_applicable。
- 对具体论断：supported/unsupported/contradictory/unknown。
- 对任务：可继续回答、需补参数、需查当前业务事实或需人工审核。

不得把无资料时正确拒答标为“知识充分”；也不能把正确的有限回答一律判错。

### 12.4 缓存策略

检索缓存绑定查询、授权空间、epoch、Embedding指纹、重排模型/算法、top_k/recall_k/rerank_k和策略版本。瞬时busy/deadline不写普通成功缓存。

回答缓存绑定用户、相关上下文、完整证据fingerprint、模型/提示/schema/Judge/业务策略版本。仅缓存已通过审查的无副作用回答；拒答、转人工、未知、降级和业务动作结果不入回答缓存。

## 13. DEV-08 回答构建、审查与发布

**优先级：P0/P1；阶段N6；验收组AC2-08。**

### 13.1 三个组件

| 组件 | 输入 | 输出 | 不应承担的职责 |
| --- | --- | --- | --- |
| AnswerBuilder | Task/TurnContext、EvidenceBundle、回执 | 模板或DraftCandidate | 不写最终消息，不执行新业务动作 |
| AnswerReviewer | 问题、候选、证据、策略快照 | ReviewDecision与安全错误码 | 不把模型自检或排名当结论，不自动改标签 |
| ResultPublisher | 通过审查的正文或可信流程说明 | PublishedResult与持久事件 | 不重调用模型、不重做未知写操作 |

迁移顺序：先提取纯组装/校验接口并建立对照测试，再替换response_node的委托，最后逐个删除旧分支。无证据提示、补槽、模板、缓存、人工结果都必须经过最终发布底线。

### 13.2 分层审查

1. 知识/政策/资源版本和当前证据身份有效。
2. 业务关键事实与所有相关成功回执一致：对象、金额、币种、状态、真实/模拟、是否已登记/支付。
3. 引用确实属于当前证据，版本、quote及正文身份一致。
4. 结构化Judge分别评价可回答性、回复行为、候选有效性与关键论断。
5. 程序联合判定，critical问题不能由其他高分抵消。
6. 最终发布检查覆盖敏感内容、能力声明和未支持承诺。
7. 发布前绑定候选/证据/策略hash；候选改变必须重新审查。

独立Judge指独立调用，不自动表示不同模型或独立正确性。候选可比较不同模型，但仍需人工复核数据和程序保护。

### 13.3 v2现有缺口的处理

最新真实v2结果中六条边界绑定unknown，原失败原始判决未保存，不能离线恢复精确字段原因。先用合成契约反例复现候选/quote/segment覆盖等失败类型，补充经过脱敏、限量、访问受控的诊断字段或加密评测制品，再准备新冻结方案。

不要根据100条反例局部零误放直接激活v2。unknown、正确补问误拒、原程序固定保护与Judge单独判定须分别统计。正式模型复验需要新额度。

### 13.4 失败处理

- 证据不足：补问、有限回答或无据拒答；记录原因，保持业务只读。
- 候选存在可修正质量问题：预算允许时最多重生成一次，替换后完整复核。
- 业务权限或动作资格拒绝：给出允许范围，不让模型编造绕过步骤。
- Judge关闭/超时/非法/绑定失败：对于需要语义审查的政策候选fail-closed；可信流程提示仍可按对应程序契约发布。
- 人工请求失败：描述“无法确认登记结果”，不宣称已接通。
- 业务已提交而回答失败：保留业务事实，以已核实回执恢复，不因文本失败重做业务。
- 所有重试共享总期限/尝试预算；不能为了完成回答绕过最后一次审查。

**优先级：P0/P1；阶段N1持续至N6；验收组AC2-09。**

### 14.1 类型与迁移

建立状态字段清单：owner、生命周期、读写入口、持久位置、兼容投影、失效规则。沿用已有BusinessParameters、RefundPreview/ActionView、TurnRefundConfirmation、GenerationMetadata、ToolObservation、QueryRewriteObservation和TurnFlow，逐项补齐未声明状态。

兼容字典只允许单向投影；已建立或显式清空的类型状态不能被旧键复活。禁止工具data展开到身份、证据、确认或流程控制字段。SQL历史context_data恢复仍执行同一白名单与验证。

### 14.2 ContextBuilder

输入：可信主体、当前消息、Task摘要、最近相关消息、用户允许的偏好、当前动作引用。

输出：不可变TurnContext与上下文选择记录。记录选取的消息ID、摘要版本、估算tokens、删减类别及截断原因；默认不把完整用户文本写到一般Trace。

保留顺序：当前消息与安全约束→当前动作/任务事实→必要证据→最近相关对话→长期偏好。超预算时移除低优先级背景，不截掉政策必要条件或偷偷降低审查标准。

### 14.3 长期记忆

MemoryEntry按用户隔离，区分偏好与用户陈述；保存来源、可见范围、版本、到期、用户确认及删除状态。写入规则显式，默认不保存密钥、支付信息、证件或第三方隐私。

提供查看、纠正、删除和关闭记忆入口；删除后检索缓存、派生索引和后续上下文同步失效。已有审计保留按策略脱敏或引用化处理，不能以“忘记”删除业务必要回执。

评测覆盖“记住了什么”和“记忆是否错误影响行为”，不能只验证召回命中。

## 15. DEV-10 持久执行、事件与后台任务

**优先级：P0/P1；阶段N3；验收组AC2-10。**

### 15.1 API与Worker分工

当前start()创建进程内任务。目标引入chat_run类型的SQL持久领取，API只负责接受和查询；Worker通过原子条件更新/事务领取已接受Run，并继续使用会话租约与版本fence。

先扩展现有SQL BackgroundJob与Worker模式，评测证明SQL领取不足时再考虑消息中间件。无需同时引入多套队列。

领取后建立run owner token、期限和续租；失租禁止后续模型出口、工具写入及最终提交。API退出不丢失已接受Run，Worker退出后由新Worker按状态和回执接管。

### 15.2 检查点与恢复边界

| 操作 | 可以如何恢复 | 禁止行为 |
| --- | --- | --- |
| 尚未执行的只读步骤 | 依据冻结计划和期限重新执行 | 使用当前新策略冒充原Run策略 |
| 已完成只读结果 | 在版本/TTL/权限有效时复用 | 使用过期订单状态决定退款 |
| 已完成模型输出 | 校验绑定和schema后复用 | 用新模型重新生成却仍声称原输出 |
| 写工具发出但无回执 | 先查询幂等键/业务回执 | 因客户端超时直接重发 |
| 写工具已提交 | 读取回执继续组织/校验响应 | 再提交一次同类动作 |
| 待用户确认 | 持久化等待，释放执行资源 | 后台自动确认 |
| 会话关闭/删除 | 停止后续操作并保留审计 | 迟到Worker复活会话 |

LangGraph恢复可能从节点开头重入，含外部副作用的步骤必须独立可幂等，并有持久执行记录；不能依赖“恢复后从下一行继续”的假设。[EXT-01]

### 15.3 事件与发布

阶段事件、消息终态、Run结果有单调sequence，公共payload可验证且有event_version。阶段事件只说明真实已发生阶段，不含草稿、隐藏推理、敏感参数或未经确认的成功声明。

最终消息、Run终态、最终事件与摘要Job同一事务提交；对外业务服务若已经独立提交，凭回执对账，不虚构跨服务原子事务。

WebSocket持续读取已提交事件，避免当前“等待完整Run后集中发送进度”；支持after_sequence补读、乱序缓冲和去重。Redis通知可减少轮询，但SQL事件仍为事实源。慢客户端有界缓冲，可断开后补读；不能阻塞业务提交或取消已提交动作。

取消采用明确状态与可取消范围；客户端断线、超时或关闭页面不自动等于业务取消。通知采用至少一次投递、幂等和unknown对账，不宣传通用恰好一次。

## 16. DEV-11 人工接续与坐席工作流

**优先级：P0/P1；阶段N7；验收组AC2-11。**

- 引入真实support角色、坐席身份与SQL目录/可用状态，逐步移除内存默认坐席的事实职责。
- HandoffPackage包含用户目标、产品/订单引用、已核实事实、已尝试排障、用户反馈、证据版本、已创建动作、未知项及最近必要消息。
- 接续包区分“模型摘要”“用户陈述”“工具事实”；坐席可展开来源，不能把摘要当授权凭据。
- 领取/分配使用SQL原子状态转换、容量校验与乐观版本；同时领取只有一名成功。
- 在客户界面如实展示已登记、待分配、已分配、处理中、已解决；实际聊天连接另定义状态。
- 人工接管后Agent不继续自动执行业务；模型可作为坐席辅助，但提交仍由坐席角色与服务授权。
- 接管事务同时变更Task归属/版本，后续Agent写入必须核验当前Task状态与fence；接管前已提交的动作纳入接续包，不重复执行或伪装撤销。并发接管不能只靠进程内布尔标记。
- 坐席回复记录真实actor及owner，不冒充客户；客服代办与客户确认使用不同授权契约。
- 解决、退回、重新分配、超时提醒均有原因和审计；未知通知不当作客户已收到。
- SLA按版本化工作时间/时区规则计算；首版明确固定服务时间，不编造实时排队或承诺。

## 18. DEV-13 模型平台、费用与性能

**优先级：P0/P1；阶段N8，契约从N1开始；验收组AC2-13。**

### 18.1 Provider契约

统一普通/结构化/工具/流式调用适配、模型版本与能力声明。声明支持某能力必须有对应真实协议验证；SDK替身只证明适配器路径。

主模型先保留现有配置作基线，理解模型/Judge候选独立评测。Embedding和Reranker不随聊天模型切换。升级依赖或模型时冻结版本、prompt/schema、tokenizer、量化方式与输出预算。

### 18.2 预算与计量

- 所有实际出口先SQL原子预留请求、tokens/估算费用及共享并发槽。
- 理解、修复、规划、生成、Judge、备用Provider、摘要和评测都走同一受控出口及主体scope。
- 缺usage、部分usage、请求发出无结果分开，保留unknown/estimated，不按0结算。
- 未发送失败可核实后释放预留；已发送未知不能因为换进程或重启清账。
- 费率、币种、单位、缓存计费及账户倍率随记录持久化；未核对账单时明确估算。
- 每个Run总预算和模型阶段子预算共同生效；SQL网关故障停止新模型派发。
- 运行时账本与评测授权账本分开，真实评测不能借用业务额度或旧授权。

### 18.3 GPU与调度

8GB共享显存条件下先确定一个可重复部署档位。分别测量Embedding、Reranker、可选理解模型的显存、冷启动、吞吐和队列时间，再决定驻留或按需加载。

优先复用常驻客户端、缓存不可变索引、避免重复改写；跨请求微批/Redis资格/ONNX等已有候选只有在排序、质量、完成率和延迟共同通过后采用。不能把更快拒绝请求视为容量提高。

前台与后台索引共享预算并有公平性和等待上限；后台饥饿、取消、续租、迟到返回分别验证。同GPU不同进程的实际推理完成无法仅靠HTTP超时推定。

### 18.4 性能口径

按模板、业务查询、政策RAG、复杂诊断、提交/回执恢复分别报告；区分冷/热索引、缓存、串行/并发、mock/真实模型。排队计入用户总耗时。

现有重排P95≤2000ms历史门槛保持独立，未通过仍记FAIL。新产品档位采用配套文档中的独立指标，不能替代旧门槛或更改历史分母。

## 19. DEV-14 数据、API与Python后端工程

**优先级：P0/P1；阶段N3持续；验收组AC2-14。**

- API负责鉴权、契约、接受/查询和传输；应用服务负责用例；领域服务负责业务规则；仓储负责持久化。
- 当前退款、工单、知识版本和模型账本服务优先复用，逐模块消除多源实现，避免一次性全目录改名。
- 公共API使用严格Pydantic schema、统一错误码、分页、稳定排序、乐观版本和幂等键；禁止未过滤ORM实体直接返回。
- MySQL为部署主数据库，SQLite只作明确兼容/测试档位；CAS、行锁、金额和并发语义在真实MySQL复验。
- 金额继续使用Decimal/精确字符串与币种，禁止float参与资格或结算。
- 新表/列/索引使用Alembic增量迁移；不修改已部署历史迁移，不在请求里执行DDL。
- 根据实际查询建立索引，使用EXPLAIN、查询次数和样本规模验证；避免会话历史全量加载与N+1。
- 异步API不执行阻塞模型推理或文件解析；线程/进程任务有队列与截止，取消不能被当作底层任务已停止。
- 服务身份、资源owner、当前消息、Task、Run、Action和审计建立关联；不依赖原始聊天文本恢复业务事实。
- 制定错误分类：invalid_request/unauthorized/conflict/busy/dependency_unavailable/deadline/unknown_result/internal_error；前端和日志可关联但不泄漏内部细节。

## 20. DEV-15 安全、隐私与权限

**优先级：P0；贯穿所有阶段，N8集中审计；验收组AC2-15。**

威胁模型至少覆盖：IDOR、跨会话证据、角色越权、Prompt注入、工具回包污染、确认重放、知识投毒、文件上传攻击、MCP越权、SSRF、XSS、Token泄漏、日志泄漏、模型数据外发和拒绝服务。

具体措施：
1. 身份只由可信认证建立；每个资源入口独立验证owner、support分配或admin权限。
2. 底层工具服务再次校验，保护REST/WS/MCP/Worker/恢复入口；菜单隐藏不能替代后端授权。
3. 用户历史、知识文档、工具结果均为数据，不能授予权限或改变系统策略。
4. 确认/预览签名或服务端绑定含当前身份、资源、版本、参数和到期；动作状态变化立即失效。
5. 密钥通过环境或密钥管理注入；普通日志、Trace、前端、报告和版本库不得含凭据/完整个人数据。
6. 网络出口固定允许的Provider与MCP目标；不接受模型生成任意URL；上传和引用展开限制协议与路径。
7. Cookie/Token策略、刷新并发、CORS、WebSocket认证、连接限流、错误码和过期行为有明确测试。
   浏览器WebSocket拟使用短时、单用途、绑定身份/会话的连接票据；不在URI长期携带访问Token，所有接入日志屏蔽凭据和敏感查询参数。票据消费、过期和重放必须验证。
8. 调试器、评测原始输出和模型调用详情按角色授权；一般运营页面仅展示脱敏摘要。
9. 删除/更正用户记忆与个人数据有范围、保留期和审计规则，不删除必须对账的业务回执。
10. 演示环境不使用真实用户数据；生产配置关闭演示账号、使用强密钥与明确origins。
11. P0固定安全集全部通过才能继续灰度；不把固定集零失败写成通用“零风险”。

## 26. 切片实施模板与回退

每个DEV切片必须记录：
- 目标问题、用户触发方式、当前与目标行为。
- 修改路径、可信边界、数据/接口/配置影响。
- 关联AC2编号、测试层次、固定输入与预期副作用。
- 新增/修改回归、执行命令、源码起止hash、失败与未运行项。
- 数据备份与回退步骤、旧版本兼容期限、发布开关。
- 实际验收结果与证据位置；不得以代码完成率替代验收结果。

采用expand→backfill→compare→switch→observe→contract：
1. 新增兼容字段/表与适配，不删除旧事实。
2. 可恢复、分批、幂等回填；校验数量、引用和hash。
3. 只读对照/影子验证，不执行双份业务写。
4. 新Run按固定策略切换，旧Run/Action按原版本继续或明确终止。
5. 观察完成率、unknown、回执一致性与预算。
6. 达到删除条件后再退役兼容键/旧入口，保留历史读取能力。

紧急回退先停止接受候选新Run，保留账本/业务回执；清理未知操作必须经过对账。知识回退使用明确发布版本和新epoch，不能从备份覆盖正在运行的全部数据。

## 27. 目标指标与验收绑定

所有数字均为后续冻结目标，不是当前已达到的效果。完整公式、数据规模与通过条件以配套验收文档为准。

| 领域 | 新目标摘要 | 说明 |
| --- | --- | --- |
| 理解 | Macro-F1≥0.90，请求类型≥95%，关键实体≥97% | 与历史M4底线对齐，新增条件/多诉求分项 |
| 关键保护 | 固定安全集越权/未确认写/重复提交=0 | 仅描述固定集；不能外推所有输入 |
| 检索 | Recall@20≥95%，nDCG@5≥0.85，必要条件覆盖≥95% | 独立留出，按产品和政策分层 |
| 审查 | 固定负例误放≤2%，正例误拒≤5% | 另外统计unknown、正确边界回复、真实生成论断支持 |
| 真实生成 | 人工逐论断支持率≥97%，适当边界处理≥95% | 预先定义分母，缺资料不以拒答数量充成功 |
| 任务 | 封存多轮任务完成率≥90% | 同时检查业务SQL终态及不应发生的动作 |
| 性能 | 依路径/硬件/Provider档位冻结 | 保留历史重排2秒门槛，不能用新档位替代 |
| 发布 | 未通过P0=0；P1全部有对应层次证据 | P2未做可明确延期，不将BLOCKED写成PASS |

质量、性能和正确恢复必须在同一候选版本/声明档位下联合验证，不能拼接不同模型、不同代码或不同负载的最佳数字。

## 28. 主要风险与控制

| 风险 | 控制 | 触发停止/回退条件 |
| --- | --- | --- |
| 同期编辑导致正式证据失效 | 隔离冻结工作树/镜像、起止hash、评测所有者 | 源码/数据/配置漂移，报告INVALID_EVIDENCE |
| 小显存模型竞争 | 固定部署档位、客户端复用、背压与分阶段实测 | OOM、完成率或延迟失败；不强行常驻更多模型 |
| 更自主后误动作增加 | 只读能力视图、固定写流程、原领域检查 | 未确认写或越权，立即关闭候选 |
| Judge同源误判或过度拒绝 | 程序规则、边界契约、独立人工数据、双分母 | 误放/误拒/unknown任一不达标 |
| 工作流恢复重复副作用 | operation_key、持久回执、fence、未知对账 | 不可核实重复或回执不一致 |
| 状态重构损坏历史会话 | 白名单迁移、兼容读取、回填对照、备份 | 预览/确认范围或历史引用异常 |
| 知识条件丢失/旧版复活 | 完整有界片段、CAS、epoch与Job fence | 撤销后旧证据可见或迟到发布 |
| 拓展范围失控 | 三场景主线、DEV/AC2追踪、阶段冻结 | 无验收用例、无业务价值的新栈进入关键路径 |
| 付费预算绕过 | 新固定授权、网关账本、重试计数、无余额停止 | 任何未授权派发，停止真实调用并审计 |
| 外部服务仍为模拟 | UI/API/回执一致标识 | 对用户宣称真实支付/通知/连接而无证明 |
